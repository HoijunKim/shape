# V1: DataTable huge-file virtualization (beyond Blink's height cap)

> **For agentic workers:** implement task-by-task, TDD for every pure function, and a jsdom wiring test + a `wails build` for the component change. Every test states its mutation and confirms it kills the test. This repo has chronically shipped cannot-fail tests. **This plan was adversarially reviewed (workflow wiec8kvvi, 19 findings); the design below is v2 - the review's survivors are folded in, so do NOT reintroduce a JS-repositioned scroll-linked rows layer (see decision 6) or a header-blind fill (see decision 5).**

**Goal:** Make EVERY row of a file reachable and the file's TRUE LAST ROW visible at the bottom of a scroll. Today `DataTable.svelte` sizes its scroll container with `height: HEADER_H + total * ROW_H`. Blink (WebView2/Chromium) caps element height at 2^25 physical px; divided by `devicePixelRatio` and `ROW_H` (28) that ceiling lands around 600k–800k rows (confirmed live on a 4M-row source, `gui/README.md`), past which the browser clamps the scrollable area and the tail is unreachable, with no go-to-row affordance either.

**Approach:** A DPR-aware cap on the scroll spacer; a **scaled** scroll→row mapping when (and only when) the file exceeds the cap; a **natively `position: sticky`** rows window in scaled mode (Blink pins it to the viewport on the compositor - NOT a JS scroll-linked reposition, which lags a frame and shears); and a **go-to-row** input for exact navigation. The vast-majority small-file path stays **byte-identical** to today (unscaled, native 1:1 absolute rows), so every existing DataTable/widths test passes unchanged.

**Tech Stack:** Svelte 3.49 + vitest. Pure scroll math in `widths.ts` (vitest cannot reach functions inside a `.svelte` file). **No new dependency, frontend-only, cgo-free.**

**AUTHORITATIVE SOURCES:** `gui/frontend/src/lib/explorer/DataTable.svelte` (`recomputeRange` L63-120; `.viewport`/`.content`/`.rows` layers - `.viewport{overflow:auto}` L357, `.content{position:relative}` L361, `.rows{position:absolute; top:HEADER_H}` L414/302, `.row{position:absolute; top:i*ROW_H}` L420/308; the sticky `.header`/`.corner`/`.gutter-cell` L344/352/409; the rAF `onScroll` L123-129; the `$: safeTotal, recomputeRange()` L141, `resetToken` L191, `columns`-change L146 triggers; the `visibleRows` IIFE with `effectiveFirstRow` L209-225; the gutter `{row.index}` L298-304), `widths.ts` (`rowWindow` L63-76, `columnAt`, `clamp`), `paging.ts` (`pageRowsFor`/`pagesForRange`/`rowLocation`/`reconcileEof` - the fetch machinery this plan does NOT change), `store.ts` (`ensurePages` L218-306 called with ABSOLUTE indices, `rowAt` L308-315). ## Decisions locked before this plan (do not relitigate)

1. **Only the VERTICAL axis scales.** Columns are capped at `MaxColumns=512` and widths at `MAX_W=320`, so the widest content is 512×320 = 163,840 px - orders of magnitude under any cap. The horizontal machinery is untouched.
2. **The fetch machinery is UNCHANGED.** `pagesForRange`, `rowLocation`, `rowAt`, `reconcileEof`, `PageCache`, `ensurePages` all key on the ABSOLUTE row index. This plan changes only how DataTable derives the visible row *window* from `scrollTop` and where it *positions* the rendered rows. A row's page/fetch are identical whether or not the view is scaled.
3. **The unscaled path stays byte-identical to today.** When `HEADER_H + total*ROW_H <= cap`, `contentHeight` is exactly `HEADER_H + total*ROW_H`, the scroll→row mapping is exactly today's `floor(scrollTop/ROW_H)` (the current `rowWindow`), the `.rows` layer stays `position:absolute; top:HEADER_H`, and rows render at absolute `top: i*ROW_H`. Scaling is a strictly additive branch reached only past the cap. Every existing widths/DataTable test must pass with NO edit - that untouched suite (not the new byte-identity battery) is the real guardrail against a small-file regression (review V9/#9).
4. **The cap is DPR-aware, margin-guarded, and re-read on BOTH resize AND a resolution change.** Blink's limit is physical (2^25); the CSS cap is `floor(2^25 / dpr) - CAP_MARGIN_PX`. The `/dpr` model is what reproduces this repo's own empirical ~800k-row ceiling at a typical dpr≈1.5 (review V5 refuted the "it's CSS-px, drop the /dpr" objection: the CSS-only model predicts a fixed ~1.2M ceiling that contradicts the observed ~800k). `devicePixelRatio` changes when a window is dragged between monitors of different scale and **does NOT reliably fire a `resize` event** (review V2/#3), so DPR is observed via `window.matchMedia('(resolution: <dpr>dppx)')`'s `change` event (re-armed after each change), in ADDITION to the resize handler (which covers `clientHeight` changes). Both are guarded for jsdom, where `matchMedia` is `undefined` and `devicePixelRatio` is 1.
5. **Scaled `scrollTop`→row mapping accounts for the sticky header and fills to the true tail.** `visibleRows = max(1, floor((clientHeight - HEADER_H) / ROW_H))` - the rows that fit in the band BELOW the sticky header (NOT `ceil(clientHeight/ROW_H)`; the header-blind count is the review's CRITICAL finding V16/#12, which left the last ~10 rows below the fold). `denom = contentHeight - clientHeight`; `frac = denom > 0 ? clamp(scrollTop/denom, 0, 1) : 0` (the `denom <= 0` guard neutralises the div-by-zero the small test cap exposes, review V10/V14). The top visible row is `firstVisible = round(frac * max(0, total - visibleRows))`. So `scrollTop=0 → firstVisible 0`; `scrollTop=maxScroll → firstVisible = total - visibleRows`, which places rows `[total-visibleRows .. total-1]` exactly in the band with **`total-1` at its bottom edge, on-screen**. The returned window widens `firstVisible`/`lastVisible` by overscan, clamped to `[0, total-1]`.
6. **In scaled mode the rows window is NATIVELY sticky - never JS-repositioned.** A JS reposition of a child of the natively-scrolled `.content` (the v1 `top: scrollTop+HEADER_H` idea) lags the compositor by a frame and shears the whole grid during scroll (review V1/V3/V8/V15 - CONFIRMED against the real compositor model). Instead: `.content` stays the cap-height spacer that sizes the scrollbar; a `.rows-window` element is `position: sticky; top: HEADER_H; height: {max(0, clientHeight - HEADER_H)}px; overflow: hidden` - Blink pins it to the viewport with ZERO JS, exactly like the existing sticky `.header` (`top:0`), and its `overflow:hidden` keeps its abs children from inflating `.viewport.scrollHeight` (review V3/#2). Inside it, each visible row renders at `top: (i - windowFirstRow) * ROW_H` (overscan-above rows take small negative tops, clipped by `overflow:hidden`). JS (on the rAF `onScroll`) only swaps WHICH rows the window holds by recomputing `windowFirstRow`; the layer itself never moves under JS control, so there is no shear. Content still updates at rAF cadence, so a very fast flick shows a brief content-lag (not a position shear) - an inherent, honestly-documented property of any virtual list past the native 1:1 cap. In the unscaled path the structure is exactly today's (decision 3).
7. **`recomputeRange` reads back the CLAMPED scrollTop and the window+effectiveFirstRow are reactive.** `recomputeRange` always uses `viewportEl.scrollTop` (the browser-clamped value, read after any assignment - review V4 confirmed this is already the pattern), and it assigns the window bounds AND `effectiveFirstRow` to component-level reactive state (not an IIFE local - review V19/#19: the template's `rowTopFor(i, effectiveFirstRow, …)` must see the clamped value, or a `reconcileEof` shrink frame renders rows at negative tops). The reactive triggers include `cap`, `contentHeight`, and `scaled` (`$: cap, contentHeight, scaled, recomputeRange()`), so a mid-session DPR change re-derives the window immediately rather than waiting for an incidental scroll (review V17/#17).
8. **Go-to-row is exact against the CURRENT (possibly estimated) total.** A 1-based input clamps to `[1, total]`, sets `viewportEl.scrollTop = scrollTopForRow(row-1, …)`, then `recomputeRange` reads the clamped scrollTop back. It is "exact" in the operational sense that typed row N lands row N in the rendered window against the live `total`; on the rescan tier `total` is an estimate that `reconcileEof` corrects as pages land, so go-to-row inherits that estimate exactly as drag-scroll does - the doc says so rather than promising more (review V11/V18). No claim of exactness "regardless of row count": past the point where scroll quantisation makes consecutive addressable rows more than a window apart (~1e9 rows), the honest caveat stands.
9. **`resetToken`→row-0 and the `safeTotal`-shrink clamp still hold** because they run through the same `recomputeRange`/`scrollToTop`, now reading the scaled mapping and the reactive `effectiveFirstRow`.
10. **Out of scope:** horizontal scaling (impossible under the column/width caps), a minimap/scrubber, a "row N of M" hover tooltip, keyboard PageUp/PageDown/Home/End (note it as a follow-up - the review flagged it as a scope gap, but it is additive and not required for reachability), and any Go/engine/fetch change.

### Task 1: Pure scroll math in `widths.ts`

**Files:** `gui/frontend/src/lib/explorer/widths.ts` (+ `widths.test.ts`).

**Interfaces (produces):**
- `export const BLINK_MAX_PX = 33_554_432` (2^25), `export const CAP_MARGIN_PX = 1_000_000`, `export const CAP_FLOOR_PX = 200_000` (a sane minimum so a huge dpr never collapses the cap below several viewports).
- `capForDpr(dpr): number` → `max(CAP_FLOOR_PX, floor(BLINK_MAX_PX / max(1, dpr)) - CAP_MARGIN_PX)`.
- `contentHeightFor(total, rowH, headerH, cap): number` → `min(headerH + max(0,total)*rowH, cap)`.
- `isScaled(total, rowH, headerH, cap): boolean` → `headerH + max(0,total)*rowH > cap`.
- `visibleRowCount(clientHeight, headerH, rowH): number` → `max(1, floor((clientHeight - headerH) / rowH))`.
- `rowWindowFor(scrollTop, clientHeight, total, rowH, headerH, overscan, contentHeight): {firstRow, lastRow}` - when NOT scaled (`contentHeight === headerH + max(0,total)*rowH`) it MUST return exactly `rowWindow(scrollTop, clientHeight, total, rowH, overscan)` (delegate, so the unscaled result is literally the same function); when scaled it uses decision 5's header-aware fractional mapping with the `denom<=0` guard, widened by overscan and clamped to `[0, total-1]`, never exceeding `total-1`.
- `scrollTopForRow(row, clientHeight, total, rowH, headerH, contentHeight): number` - the inverse of decision 5 (unscaled: `row*rowH`; scaled: `fracForRow * (contentHeight - clientHeight)` with `fracForRow = row / max(1, total - visibleRowCount(...))`), clamped to `[0, max(0, contentHeight - clientHeight)]`.
- `rowsLayerTop(headerH): number` (constant `headerH` - the sticky layer's `top`, same in both modes; the layer is native-sticky, not JS-translated) and `rowTopFor(i, firstRow, rowH, scaled): number` → `scaled ? (i - firstRow)*rowH : i*rowH`.

- [ ] **Step 1: Write failing tests** in `widths.test.ts`:
  - `contentHeightFor` caps a huge total, is exact under the cap; `isScaled` flips exactly at the boundary; `capForDpr` shrinks as dpr grows and never drops below `CAP_FLOOR_PX`. **Mutation: drop `- CAP_MARGIN_PX` → a dpr=1 total sized exactly at 2^25 is not flagged scaled.**
  - `visibleRowCount` subtracts the header: at `clientHeight=800, headerH=32, rowH=28` it is `floor(768/28)=27`, NOT `ceil(800/28)=29`. **Mutation: use `ceil(clientHeight/rowH)` → this fails (the header-blind count that hid the tail, V16).**
  - Unscaled `rowWindowFor` returns byte-identical windows to `rowWindow` for a battery of under-cap `(scrollTop,total)` pairs. **This battery's real mutation is an UNSCALED off-by-one in the delegation (e.g. `floor`→`ceil`), which it DOES kill; do not cite it as the scaled-regression guard (that guard is the untouched existing tests) - review V9.**
  - Scaled `rowWindowFor`: `scrollTop=0 → firstRow 0`; **`scrollTop=maxScroll → the window's last row is exactly `total-1` AND its first row is `total - visibleRowCount`** (the tail fills the band). **Mutation: use `floor(scrollTop/rowH)` in the scaled branch → the maxScroll case does not reach `total-1` (the tail is unreachable).** `denom<=0` (a tiny cap with `clientHeight >= contentHeight`) returns `firstRow 0`, not NaN. **Mutation: remove the `denom<=0` guard → NaN bounds.**
  - `scrollTopForRow` round-trips: `scrollTopForRow` then `rowWindowFor` lands the target row within `[firstRow, lastRow]` at both ends and a mid row (±1). **Mutation: use `row*rowH` unconditionally → on a scaled fixture the mid row is not in the returned window.**
- [ ] **Steps 2-4** (implement → PASS + `npm run check`). **Step 5: Commit** - `feat(gui): dpr-aware scroll cap and header-aware scaled row-window math`.

### Task 3: Go-to-row affordance

**Files:** `gui/frontend/src/lib/explorer/DataTable.svelte` (a slim input in the corner cell or a small control) + `DataTable.test.ts`.

Works in both modes; in scaled mode it is the exact-navigation path past the coarse drag.

**The risk this plan is built around:** a virtual scroll past the native height cap cannot be both 1:1-smooth AND unbounded - the honest design is a native-sticky window (no shear) whose CONTENTS update at rAF cadence (brief content-lag on a fast flick), with the tail guaranteed on-screen by a header-aware fill and go-to-row as the exact backstop. The v1 mistake the review caught - JS-repositioning a compositor-scrolled child - is explicitly forbidden by decision 6.
